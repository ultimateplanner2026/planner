the cause, measured, and how I fix it

Both of your symptoms are one bug. The planner listens to the cloud so changes arrive without a refresh — and that listener can die without saying so. A phone going to sleep, a lid closing, a network switching: the connection drops but no error is raised, so the app still believed it was listening and never rebuilt it. The only thing still moving data was a once-a-minute pull, which is exactly why refreshing appeared to fix it.

Driven with two devices and a listener silenced the way a dropped connection silences one:

added on the other devicenever arrived11.7 s
deleted on the other devicenever arrived12.2 s
The fix stops guessing: it compares the version this device last applied against the version the cloud actually holds. If the cloud is ahead and the listener has not said so, the listener has missed something — rebuild it and take the change.

The picture shows: the same task added on the phone, the same 9 AM slot, the same crop on the browser.

I also thought of — you have not decided this yet

A second, smaller fault in the same place. When you pick a device up it reads the cloud — but that read shared a timer with the once-a-minute pull, so picking it up shortly after one read nothing. It has its own clock now, which is the other half of "when I went to the planner on my phone, it was still showing there".

I got this wrong twice before getting it right, and the test caught both, not me. First I tried "if it has been quiet for 90 seconds, assume it is dead" — but a healthy connection is also quiet when nothing changes, so silence proves nothing. Then I tried checking less often while it looked healthy, which broke recovery completely: a listener that has just died still looks healthy.

The cost, stated plainly: one small read every 15 seconds, skipped entirely while the tab is hidden. Worst case about 23% of your free cloud allowance with a tab open all day; in practice far less. That is the price of "what I did on my phone shows up here without refreshing".
