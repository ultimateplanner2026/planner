the cause, measured, and how I fix it

What I measured, driving your own gesture. Two separate things happen, and only the second one is a defect:

1. The drag itself WRITES a date. Dropping a tree item on the day calendar sets date to that day and time to the hour you dropped on. That is the drag doing its job — the calendar is not showing an undated item, it is showing one the drop just dated. Nothing wrong there.

2. You then cannot undo it. You emptied the Due Date box and pressed Save — and the save was refused, with the red message "Pick a location first — every task lives in a branch." The date stayed written and the activity stayed on the calendar, while the box in front of you read empty. That is the fault, and it is the one in your picture.

Why it happens. There is a rule that a task must sit in a branch before it can be saved. It was written to stop a task being created adrift. But it checks every save, including a save whose only effect is to remove a date — which takes something off the calendar and leaves it in the tree. That direction is always safe, so the rule should not block it.

The fix, in one sentence: if the only change is that the Due Date box has been emptied, the save goes through even with no branch chosen. Giving an unbranched task a date is still refused, exactly as now — I tested that half too, because a fix that quietly switched the rule off would look identical in your picture.

The picture shows: ['your exact state reproduced: unbranched + dated, Save refused, item stays put', 'the toast you would see is quoted from the running build, not from my memory', 'on the fix: no toast, stored date null, zero chips on the calendar', 'AND the opposite case - giving an unbranched task a date is STILL refused', 'so the branch rule is narrowed, not disabled - both halves measured']

And the second case: the same thing from the calendar’s side — because the dialog covers the calendar, the picture above cannot show both at once. This is what you were looking at when you circled it.
